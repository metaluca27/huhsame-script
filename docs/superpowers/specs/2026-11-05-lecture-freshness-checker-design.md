# 강의자료 유통기한 검사기 설계

제1회 라이너 해커톤(.EXE-THON) 출품작 설계 문서. 작성일 2026-11-05.

## 1. 한 줄 요약

강의 PPT를 올리면 시간이 지나 낡았을 내용을 골라 공식 문서와 대조하고, 내용마다 `그대로`, `바뀜`, `확인 못 함`으로 판정해 출처와 수정안을 보여 주는 웹앱이다.

## 2. 풀려는 문제

- **누가:** 빠르게 바뀌는 도구나 제도를 가르치는 강사와 교육 담당자. 첫 사용자는 AI 도구 입문 강의를 하는 루카 본인이다.
- **언제:** 강의를 앞두고 기존 자료를 다시 쓸 때.
- **얼마나:** PPT 1개를 다시 확인하는 데 2시간 이상 걸린다(루카 실제 경험). 놓치면 수강생 앞에서 틀린 내용을 가르치게 된다.
- **증거:** 안티그라비티 강의 노트에 남아 있는 `[강사 확인 필요]` 기록과, 공식 문서에서 확인되지 않아 슬라이드에서 뺀 "플러그인 60개" 판단.

## 3. 대회 조건과 설계 대응

| 조건 | 대응 |
|---|---|
| Liner Model 또는 Search를 핵심 기능에 사용 | 검색은 Liner Search, 추출과 판정은 Liner Model이 맡는다. 둘 중 하나라도 멈추면 검사가 진행되지 않는다. |
| 대회 기간에 새로 만든 결과물 | 코드는 개발 시작일부터 새 저장소에 쓴다. 지금은 설계만 한다. |
| 내부 자료와 타인 개인정보 금지 | 시연은 루카 본인 강의 자료와 가상의 사내 문서만 쓴다. 수강생 이름, 이메일이 보이는 화면은 쓰지 않는다. |
| 크레딧과 키 노출 금지 | 키는 워커 시크릿에만 둔다. 제출 저장소와 브라우저 코드에는 넣지 않는다. |
| 제출물: 소스, 5분 이내 데모 영상, 기획서 | 저장소는 6장, 데모 영상은 10장, 기획서는 이 문서를 보완해 만든다 |

개발 시작일과 제출 마감은 홈페이지(11-12, 11-25)와 신청 폼의 일정이 어긋나 주최 측 확인이 필요하다. 8장 일정은 날짜 대신 개발 시작일 기준으로 적는다.

## 4. 사용 흐름

1. **올리기:** 사용자가 `.pptx`를 올린다. 원본은 서버에 저장하지 않는다.
2. **공식 사이트 정하기:** 에이전트가 자료의 주제를 보고 공식 사이트 후보를 제안한다. 사용자가 확인하거나 고친다. 예: `antigravity.google`.
3. **검사:** 슬라이드별 진행 상황을 화면에 실시간으로 보여 준다.
4. **결과 보기:** 왼쪽에 슬라이드, 오른쪽에 내용별 판정 카드가 나온다. 맨 위에는 판정별 개수와 걸린 시간을 표시한다.
5. **가져가기:** 수정 목록을 복사하거나 Markdown으로 내려받는다. 원본 PPT는 고치지 않는다.

## 5. 에이전트 동작

| 단계 | 하는 일 | 사용 도구 |
|---|---|---|
| 읽기 | 슬라이드 글자, 발표 노트, 슬라이드 그림을 꺼낸다 | 브라우저에서 파일 해석 |
| 골라내기 | 버전, 요금, 숫자, 날짜, 메뉴 이름, 기능 유무처럼 낡을 수 있는 내용만 뽑는다. 일반 설명은 뺀다 | Liner Model |
| 찾기 | 내용마다 검색어를 만들어 공식 문서와 변경 기록을 찾는다 | Liner Search |
| 본문 읽기 | 찾은 페이지 본문을 가져온다. Search는 요약만 주기 때문에 필요한 단계다 | 워커 |
| 판정 | 슬라이드 내용과 본문을 비교해 판정하고 근거 문장을 고른다 | Liner Model |
| 재조사 | 시간이 남으면 `확인 못 함` 항목만 다시 조사한다. 없어도 완성으로 친다 | Deep Research Agent API |

### 판정 규칙

- **`그대로`:** 공식 출처 본문에 슬라이드 내용과 일치하는 근거 문장이 있다.
- **`바뀜`:** 공식 출처 본문에 슬라이드 내용과 다른 근거 문장이 있다. 이때만 수정안을 낸다.
- **`확인 못 함`:** 위 두 경우가 아닌 모든 경우. 사람이 직접 확인할 일을 한 줄로 적어 준다.
- **근거 대조:** 모델이 고른 근거 문장이 가져온 본문에 실제로 있는지 코드로 확인한다. 없으면 `확인 못 함`으로 바꾼다. 지어낸 근거를 막는 가장 중요한 장치다.

### 출처 등급

| 등급 | 예 | 판정 근거로 쓰는가 |
|---|---|---|
| 1. 지정 공식 사이트 | 사용자가 확인한 도메인 | 쓴다 |
| 2. 같은 회사의 다른 공식 채널 | 사용자가 함께 지정한 도메인. 예: `cloud.google.com` | 쓴다. 1등급과 어긋나면 1등급을 따른다 |
| 3. 그 외 | GitHub, 유튜브, 레딧, 페이스북, 미디엄 | 쓰지 않는다. 참고로만 표시한다 |

이름에 official이 들어가도 등급을 올리지 않는다. 등급은 사용자가 확인한 도메인만으로 정한다.

### 판정 카드

- 슬라이드 번호와 원래 문장
- 판정
- 근거 문장, 출처 링크, 출처 등급
- `바뀜`일 때 수정안, `확인 못 함`일 때 사람이 할 일
- 참고로만 표시하는 3등급 출처

## 6. 구조

```text
브라우저(Firebase Hosting의 /fresh)
  - PPT 해석, 진행 관리, 결과 화면
        │ 내용 하나씩 요청
        ▼
전용 Cloudflare Worker
  - 키 보관, Liner API 호출, 페이지 본문 가져오기
        │
        ├─ Liner Search
        ├─ Liner Model
        └─ 공식 문서 페이지
```

- **브라우저가 진행을 관리한다.** 28장 PPT도 내용 하나씩 짧은 요청으로 처리해서 워커 실행 시간 제한에 걸리지 않게 하고, 진행 상황도 바로 보여 준다.
- **모듈을 나눈다:** PPT 해석, 내용 추출, 검색, 본문 가져오기, 판정, 근거 대조를 각각 따로 시험할 수 있게 한다.
- **전용 워커와 새 저장소를 쓴다.** 소스를 제출해야 하므로 공용 워커의 다른 앱 코드가 섞이지 않게 한다. 전역 지침의 "공용 워커 경유"와 다른 선택이라 루카 승인이 필요하다.

## 7. 안전과 오류 처리

| 상황 | 처리 |
|---|---|
| 웹페이지 안에 AI에게 지시하는 문구 | 본문은 자료로만 다루고 지시로 따르지 않는다 |
| 워커가 임의 주소를 열람 | Search 결과에 나온 공개 `https` 주소만 가져온다. 내부망 주소는 막는다 |
| 페이지 본문을 못 읽음 | 해당 내용을 `확인 못 함`으로 두고 이유를 적는다 |
| 검색이나 모델 호출 실패 | 재시도 가능한 오류만 재시도한다. 계속 실패하면 해당 내용만 `확인 못 함`으로 두고 검사를 이어 간다 |
| 공개 페이지 비용 남용 | 파일 크기와 슬라이드 수를 제한하고, 심사 기간 동안만 키를 쓴다 |
| 사내 자료 업로드 | 올리기 화면에 기밀 자료를 넣지 말라고 안내한다. 파일 원본은 저장하지 않지만 내용은 검사를 위해 외부 API로 전달된다고 밝힌다 |

## 8. 개발 순서

개발 시작일을 1일차로 삼는다. 제출일이 앞당겨지면 3단계 이후 범위부터 줄인다. 11-13 강의와 문피아 완결이 겹치면 실제 개발은 그 뒤에 시작할 수 있다.

1. **1~2일차, 위험 확인:** 키 수령, Model의 이미지 입력 형식, 구조화된 답변 가능 여부, `antigravity.google` 본문 읽기를 먼저 시험한다.
2. **3~6일차, 핵심 흐름:** 글자와 노트만으로 올리기부터 판정 카드까지 한 번에 돌아가게 한다.
3. **7~9일차, 품질:** 정답지로 측정하며 추출과 판정을 고치고, 그림 읽기를 붙인다.
4. **10~11일차, 화면과 확장 사례:** 결과 화면을 다듬고 가상의 사내 교육자료로 한 번 돌린다.
5. **12~13일차, 제출물:** 데모 영상, 기획서, 저장소 정리, 원본과 신규 작업 구분 문구를 마무리한다.
6. **마지막 날:** 여유 시간으로 비워 두고 제출한다.

### 위험과 대안

| 위험 | 대안 |
|---|---|
| Liner Model이 슬라이드 그림을 잘 못 읽음 | 같은 키로 호출되는 다른 비전 모델을 쓴다. 그래도 안 되면 글자와 노트만 검사한다 |
| 공식 문서가 화면 렌더링 방식이라 본문이 비어 있음 | 본문을 읽는 다른 방식을 찾는다. 안 되면 해당 출처를 `확인 못 함`으로 처리하고 시연 자료를 조정한다 |
| 내용 추출이 너무 많거나 적음 | 정답지로 측정하고 내용 수 상한을 둔다 |
| 크레딧 초과 | 호출 응답의 비용 값을 기록한다. 그림 읽기는 글자가 적은 슬라이드만 돌린다 |

## 9. 검증 방법

- **정답지:** 루카의 안티그라비티 PPT에서 20개 안팎의 내용을 골라 루카가 직접 판정한 표를 만든다.
- **핵심 지표:**
  - 지어낸 근거 0건. 근거 대조가 코드로 보장하는지 자동 시험으로 확인한다.
  - 정답지의 `바뀜` 항목을 얼마나 잡아내는지
  - PPT 1개 검사 시간. 사람이 2시간 이상 걸린 일과 비교한다.
- **자동 시험:** 네트워크를 쓰지 않는 PPT 해석, 출처 등급, 근거 대조는 자동 시험을 둔다. API 품질은 정답지로 잰다.
- **제출 전 확인:** 배포된 주소에서 PPT를 실제로 올려 끝까지 돌려 본다.

수치는 측정한 값만 영상과 기획서에 쓴다.

## 10. 데모 영상 구성(5분 이내)

1. **문제:** 강의 전날, 슬라이드 28장을 다시 확인하는 강사의 화면.
2. **실행:** PPT를 올리고 공식 사이트를 확인해 검사를 시작한다.
3. **발견:** 실제로 낡은 내용을 잡아내는 장면. 어떤 내용이 잡힐지는 촬영 시점의 실제 결과를 쓰고 연출하지 않는다.
4. **차별점:** "플러그인 60개" 사례. 비공식 출처를 판정 근거로 쓰지 않고 `확인 못 함`으로 넘기는 모습. 실제 공식 문서 본문으로 다시 확인한 결과를 쓴다.
5. **임팩트:** 2시간 이상과 실제 측정 시간을 비교한다.
6. **확장:** 가상의 사내 교육자료를 같은 방식으로 검사한다.

## 11. 이번에 만들지 않는 것

- 로그인, 검사 기록 저장, 팀 기능
- 원본 PPT 자동 수정
- PDF, 구글 슬라이드, 키노트 지원
- 정기 자동 검사와 알림
- Visualization API를 쓰는 그래프

## 12. 루카에게 확인이 필요한 것

1. 전용 워커와 새 저장소를 쓰는 것(6장). 저장소 공개 여부는 제출 시 결정한다.
2. 정답지 판정 약 20개를 직접 해 주는 것(9장).
3. 주소 `/fresh`와 작품명 "강의자료 유통기한 검사기".
4. 주최 측 일정 답변에 따른 8장 조정.
