# 카카오톡 AI 상담봇 (AI트렌드 다락방)

작성: 2026-08-18 · 구축 완료: 2026-08-20 · 전 구간 검증 완료: 2026-08-21
상태: **정상 운영 중**

---

## 1. 목표

루카의 카카오톡 채널 **AI트렌드 다락방**에 24시간 응대하는 AI 상담봇(노바)을 붙인다.

랜딩페이지(`luca-darakbang.netlify.app/automation`)가 "카카오톡 24시간 AI 상담봇"을 상품으로 파는데 정작 자기 채널은 사람이 응대하고 있었다. 자기 채널을 먼저 데모로 만든다. 남의 서버를 거치지 않고 전부 자기 인프라로 돌린다.

## 2. 완성된 구조

```
손님 카톡
   ▼
카카오톡 채널 AI트렌드 다락방 (@nova_agent, pf.kakao.com/_MRAGX)
   ▼
챗봇 nova → 폴백 블록 → 스킬 Insomnia85 (Callback 켜짐)
   ▼
https://relay.infoloomia.com          (Cloudflare 터널, 고정 주소)
   ▼
미니PC(Picopulse R7) 릴레이 서버      (Docker: Go 앱 + PostgreSQL + Redis)
   ▼
오픈클로 게이트웨이 → 에이전트 nova
   ▼
AI 답변 → callbackUrl → 손님 카톡
```

**전 구간이 루카 소유다.** 제3자 서버 경유 없음.

## 5. 두 번 헤매지 않기 위한 기록

구축 중 막혔던 지점과 원인. 증상이 재발하면 여기부터 본다.

### 5-1. 공용 릴레이 `k.tess.dev` 는 죽었다
플러그인 기본 릴레이 도메인이 DNS에서 사라졌다(KT·구글·클라우드플레어 모두 NXDOMAIN). npm 최신도 0.5.1로 수정판이 없다. 공용 채널 "사만다"에 말을 걸면 자동 인사말만 오고 답이 없는 게 이 때문. **자체 릴레이 배포가 유일한 길이다.**

### 5-2. 오픈클로 게이트웨이는 조용히 죽는다
5분 내 3회 크래시하면 `crash_loop_breaker`가 걸려 **채널·프로바이더만 정지시키고 프로세스는 살려둔다.** 웹 UI가 200을 응답해 겉으론 멀쩡해 보이지만 모든 봇이 무응답이 된다. `openclaw status`의 빠른 조회로는 안 잡힌다.
→ 확인: `openclaw channels status --channel <이름>` / `~/.openclaw/logs/stability/`
→ 조치: `openclaw gateway restart`

### 5-3. docker compose 가 bcrypt 해시를 변수로 오해한다
`ADMIN_PASSWORD_HASH`의 `$`를 변수 치환으로 읽는다. `.env`에서 `$`를 `$$`로 escape 해야 한다.

### 5-4. compose 파일 자체의 YAML 오류
`${VAR:?메시지}` 안의 `: `(콜론+공백) 때문에 최신 docker compose가 파싱에 실패한다. 해당 줄 값을 큰따옴표로 감싸면 된다. (`docker-compose.yml` 49~51행)

### 5-5. 앱이 DB에 SSL을 요구한다
로컬 PostgreSQL은 SSL이 없어 `pq: SSL is not enabled on the server`로 무한 재시작한다. compose의 `DATABASE_URL` 끝에 `?sslmode=disable`을 붙인다.

### 5-6. 관리자 UI가 계정 0개일 때 터진다
`Cannot read properties of null (reading 'filter')` — 계정 목록이 `[]`가 아니라 `null`로 와서 화면이 백지가 된다. 계정을 하나 만들면 정상화된다.
계정 생성은 로그인 상태의 브라우저 콘솔에서:
```js
fetch('/admin/api/accounts',{method:'POST',headers:{'Content-Type':'application/json','X-CSRF-Token':(document.cookie.match(/csrf_token=([^;]+)/)||[])[1]},body:JSON.stringify({mode:'relay',rateLimitPerMinute:60})}).then(r=>r.json()).then(d=>console.log(JSON.stringify(d,null,2)))
```
CSRF는 쿠키 `csrf_token`을 헤더 `X-CSRF-Token`에 실어야 통과한다.

### 5-7. Admin의 "API 계정" relayToken 으로는 접속이 안 된다
릴레이 인증 미들웨어는 **세션만** 조회한다(`sessionRepo.FindByTokenHash`). 계정은 세션이 페어링된 뒤에 딸려온다. 그래서 계정 토큰을 넣으면 `/v1/events`가 401을 낸다.
→ 올바른 길은 **페어링**이다.

### 5-8. 재시작할 때마다 페어링이 풀렸다
플러그인은 세션 토큰을 메모리에만 들고 있어서, 게이트웨이를 재시작하면 새 세션을 만들고 페어링이 끊긴다.
→ 해결: 토큰을 직접 발급해 `~/.openclaw/.env`의 `OPENCLAW_TALKCHANNEL_RELAY_TOKEN`에 고정한다.
```bash
curl -X POST -H "Content-Type: application/json" -d '{}' https://relay.infoloomia.com/v1/sessions/create
```
응답의 `sessionToken`을 env에 넣고, `pairingCode`로 카톡에서 `/pair <코드>` 한 번 하면 이후 재시작에도 유지된다. 로그에 `newSession=false`가 뜨면 재사용 성공이다.
이미 다른 세션이 붙어 있으면 카톡에서 `/unpair` 먼저.

### 5-9. Callback 을 켜지 않으면 답이 갇힌다
카카오는 5초 안에 응답을 요구한다. AI는 더 걸리므로 릴레이가 `useCallback: true`로 즉답하고 나중에 `callbackUrl`로 진짜 답을 보낸다. **블록에서 Callback을 켜지 않으면 `callback_url`이 비어 와서** 답변이 전달되지 못한다(`Reply failed: Callback URL expired or not available`).
→ 위치: 시나리오 → **폴백 블록** → 우측 상단 `⋯` → **Callback 설정** → 토글 ON + 대기 메시지
→ 설정 후 반드시 **배포**. (별도 신청 절차는 없었다. 2026-03 가이드의 "Callback 권한 신청"은 현재 UI에 없다.)

### 5-10. `dmPolicy: open` 만으로는 손님이 차단된다
`allowFrom`이 비어 있으면 "all DMs will be dropped" 경고와 함께 손님 문의가 무시된다. 사업 채널이므로 `allowFrom: ["*"]`를 넣어야 한다.

### 5-11. 플러그인이 에이전트를 `main` 으로 하드코딩한다 ⚠️
```js
// dist/src/adapters/gateway.js:193
const sessionKey = `agent:main:kakao-talkchannel:dm:${normalized.userId}`;
```
`defaultTo`도 `openclaw agents bind` 라우팅 규칙도 무시하고 무조건 `main`으로 보낸다. 그래서 카톡에서 계속 푸름이(main)가 답했다.
→ 해결: 이 줄을 발신자에 따라 에이전트를 가르는 코드로 교체했다(아래 6절). 원본은 같은 폴더에 `gateway.js.orig`로 백업해 두었다.
→ **플러그인을 업데이트하면 원복되므로 그때 다시 고쳐야 한다.**
→ 대상 3곳:
```
~/.openclaw/npm/node_modules/@bartlee_xx/kakao-talkchannel/dist/src/adapters/gateway.js
~/.openclaw/npm/projects/bartlee_xx-kakao-talkchannel-3841bd8430/.../gateway.js
~/.openclaw/npm/projects/bartlee_xx-kakao-talkchannel-3841bd8430__openclaw-generation__.../gateway.js
```

### 5-12. 시나리오 블록이 폴백을 가로챈다 → 패턴 정리로 해결 (2026-08-21)
"노바야", "자동화 얼마나 걸려요?" 같은 말은 기존 시나리오 블록(`노바`, `자동화 예시`)이 먼저 잡아채서 **AI까지 가지 않는다.** 답변이 매번 토씨 하나 안 틀리면 블록 응답이다. 블록이 처리한 말은 **릴레이에 기록조차 남지 않는다**(카카오 안에서 끝나므로 스킬이 호출되지 않는다).

**판단 기준** — 블록과 AI의 역할을 이렇게 나눴다.

| 성격 | 담당 | 이유 |
|---|---|---|
| **정보** (소개, 가격 설명, 서비스 목록) | AI | 대화를 이어갈 수 있다. 고정 문구는 거기서 끝난다 |
| **행동** (신청 버튼, 상담원 연결) | 블록 | **AI는 버튼을 만들 수 없다.** 신청 의사를 밝힌 손님을 붙잡아두면 안 된다 |

블록을 지우는 게 아니라 **패턴 발화만 지운다.** 버튼은 패턴 없이도 블록으로 연결되므로 그대로 작동한다.

**정리 결과 (패턴 26개 → 9개)**

| 블록 | 전 | 후 | 처리 |
|---|---|---|---|
| 노바 | 8 | 0 | 전부 삭제. 웰컴 블록이 이미 소개하므로 중복이었다 |
| 가격문의 | 4 | 0 | 전부 삭제. `가격`·`비용` 단독 패턴이 "비용이 부담돼서요" 같은 말까지 낚아챘다 |
| 자동화 예시 | 5 | 0 | 전부 삭제. **`자동화` 단독 패턴이 최악이었다** — 자동화 컨설팅 채널이라 문의 대부분에 이 단어가 들어간다 |
| 무료진단 | 5 | 4 | `신청`만 삭제. 나머지는 명확한 신청 의사이므로 버튼을 바로 줘야 한다 |
| 상담원 연결 | 4 | 4 | 유지. 급한 손님을 AI가 붙잡으면 안 된다. 잘못 걸려도 사람 연결은 안전한 실패다 |
| 캐치올 | 0 | 0 | 원래 비어 있었다. 이름과 달리 무해 |

검증: 정리 후 "안녕하세요"를 보내니 고정 소개문 대신 AI가 답했고, 릴레이에도 `21:19:21 delivered 안녕하세요`로 기록됐다. 이전에는 이 문장이 릴레이에 도달조차 하지 않았다.

**주의**: 삭제한 문구 자체는 노바의 `SOUL.md`에 같은 내용이 들어 있어 AI가 이어받는다. 블록 문구를 크게 바꾸면 `SOUL.md`도 같이 손봐야 말이 어긋나지 않는다.

### 5-13. 포털(`/portal`)은 미완성이라 쓸 수 없다
카톡에서 `/code`를 치면 8자리 코드와 포털 주소를 준다. 코드 인증(`POST /portal/api/auth/code`)과 통계 조회(`GET /portal/api/code/stats`)는 **200으로 정상 동작**하는데, 대시보드 화면이 `GET /portal/api/me`를 호출하고 그게 401을 내면서 로그인 화면으로 되튕긴다(켜졌다 꺼지는 것처럼 보임). `/api/me`는 "포털 사용자" 로그인이 필요한 경로이고, 코드 세션에는 그 권한이 없다.

그런데 **포털 사용자를 만들 방법이 없다.** 관리자 API에는 `/api/users`의 조회·수정·삭제만 있고 생성이 없으며, 포털 쪽에도 가입 경로가 없다(OAuth 테이블은 있으나 연결된 라우트가 없음).

→ 결론: 포털은 포기하고, 통계는 DB에서 직접 본다. 봇 동작과는 무관하다.
```sql
SELECT count(*) FROM inbound_messages;
SELECT count(*) FROM outbound_messages;
SELECT to_char(created_at AT TIME ZONE 'Asia/Seoul','MM-DD HH24:MI'),
       normalized_message->>'text'
FROM inbound_messages ORDER BY created_at DESC LIMIT 10;
```

### 5-14. 릴레이가 손님에게도 개별 페어링을 요구한다 ⚠️ (릴레이 소스 패치함)
이 릴레이는 원래 **개인용** 설계다. 대화 상대(`channelID + userKey`)마다 `/pair <코드>`로 자기 오픈클로에 연결하는 구조라, **카카오톡 채널로 찾아온 손님은 전부 거절당한다.**

```
손님: "상담받고 싶은데 비용은 얼마인가요?"
봇  : "OpenClaw에 연결되지 않았습니다. /pair <코드>를 입력해주세요"
```

지인 3명으로 확인했고, DB에도 그대로 남았다(`conversation_mappings`가 전부 `unpaired`). 페어링 안 된 대화는 **저장조차 되기 전에** 거절되므로 `inbound_messages`에도 안 남는다.

→ 해결: `internal/handler/kakao.go`에 자동 연결을 넣고 이미지를 재빌드했다. 원본은 `kakao.go.orig`.

```go
// 거절 분기 바로 앞에 삽입
if (conv.State != model.PairingStatePaired || conv.AccountID == nil) && os.Getenv("DEFAULT_ACCOUNT_ID") != "" {
    defaultAccountID := os.Getenv("DEFAULT_ACCOUNT_ID")
    if err := h.convService.UpdateState(ctx, conversationKey, model.PairingStatePaired, &defaultAccountID); err == nil {
        conv.State = model.PairingStatePaired
        conv.AccountID = &defaultAccountID
    }
}
```

`.env`와 `docker-compose.yml`에 계정을 지정한다. **오픈클로 세션이 붙어 있는 계정과 같아야 한다.**

```
DEFAULT_ACCOUNT_ID=9ade925b-cd5c-4854-b628-99f469c24bd4
```

확인 방법:
```sql
SELECT status, account_id FROM sessions WHERE status='paired';         -- 오픈클로가 듣는 계정
SELECT account_id FROM conversation_mappings WHERE state='paired';     -- 일치해야 함
```

`account_id`가 바뀌면(세션 재생성 등) 이 값도 같이 바꿔야 한다. 소스를 고쳤으므로 재적용은 `docker compose up -d --build`.

**부작용**: 채널에 말 거는 사람은 누구나 AI를 쓰게 된다. 계정의 분당 60건 제한이 유일한 방어선이다. 손님은 `nova` 에이전트로만 가므로 푸름이나 루카 파일에는 닿지 않는다(6절).

### 5-15. 게이트웨이가 아무 기록 없이 사라진다 → 감시 장치로 해결 (2026-08-21)
5-2와 별개의 현상. 2026-08-20 19:33 로그를 마지막으로 게이트웨이 프로세스가 **크래시 번들도 남기지 않고** 사라졌다. 22:11에 발견할 때까지 약 3시간 동안 카톡·텔레그램·디스코드·슬랙이 전부 무응답이었다.

→ **감시 장치를 붙였다.** `~/.openclaw/watchdog/`

| 파일 | 역할 |
|---|---|
| `watchdog-gateway.ps1` | 감시 본체 |
| `run-watchdog-loop.bat` | 감시가 죽어도 10초 뒤 재실행 |
| `launch-hidden.vbs` | 창 없이 실행 |
| 예약작업 `OpenClawGateway-Watchdog` | 로그온 시 자동 시작 |

두 겹으로 확인한다. 얕은 점검만으로는 5-2 같은 "프로세스는 살아 있고 웹 UI도 200인데 채널만 정지" 상태를 놓치기 때문이다.

```
1분마다   포트 18789 응답 + 게이트웨이 프로세스 존재     → 완전 사망 감지
10분마다  채널이 실제로 connected 인지 (channels status) → 반신불수 감지
2회 연속 실패 → openclaw gateway restart → 45초 뒤 결과 확인 → 로그 기록
재시작 후 5분 쿨다운 (재시작 폭주 방지)
```

기록은 `~/.openclaw/logs/watchdog.log`. 1MB 넘으면 뒤쪽 3000줄만 남긴다.

**실제 검증(2026-08-21)** — 게이트웨이를 강제 종료하고 복구를 확인했다.
```
20:56:49  강제 종료
20:57:24  이상 감지 (1/2) — 프로세스 없음
20:58:24  이상 감지 (2/2) → 재시작 실행
20:59:50  재시작 성공 (감시 장치가 직접 확인)
채널: running, connected
```
3시간 방치되던 사고가 **3분 복구**가 되었다.

**설치 중 걸린 함정 — PowerShell 스크립트 인코딩**
`.ps1`을 UTF-8(BOM 없음)로 저장하면 윈도우 기본 PowerShell 5.1이 이를 ANSI(CP949)로 읽어 한글 주석·문자열이 깨지고 문법 오류가 난다. 정작 PowerShell 7으로 검사하면 통과해서 원인을 찾기 어렵다.
→ `.ps1`은 **UTF-8 with BOM**으로 저장할 것.
→ `.bat`은 아예 **영문만** 쓸 것. `cmd`가 CP949로 읽어 한글 주석이 깨지면 실행이 통째로 실패한다.

### 5-16. 손님은 채널을 추가해야 봇과 대화할 수 있다 (카카오 정책)
채널을 추가하지 않은 사람이 메시지를 보내면 카카오가 자체 안내로 가로챈다.

```
"'AI트렌드 다락방' 입니다. 궁금한 내용이 있으면 메시지를 입력해주세요.
 더 이상 채팅을 원치 않으시면 채팅목록에서 '채팅방 나가기'를 해주세요.
 [ Ch+ 채널 추가 ]"
```

이때 **릴레이에는 아무것도 도착하지 않는다**(`inbound_messages`에 기록 없음). 웰컴 블록은 누구에게나 뜨므로 봇이 동작하는 것처럼 보이지만, 실제 대화는 전달되지 않는다.

→ 고칠 수 없다. 카카오 채널의 기본 동작이다.
→ 테스트를 부탁할 때는 **"[채널 추가] 버튼을 먼저 눌러달라"**고 안내할 것.
→ 사업적으로는 나쁘지 않다. 채널 추가 = 친구 등록이므로 상담 한 번이 잠재 고객 명단이 된다.

증상 구분법:
| 손님이 받은 답 | 뜻 |
|---|---|
| "[채널 추가]" 버튼이 달린 안내 | 채널 미추가 (릴레이 도달 안 함) |
| 항상 똑같은 고정 문구 | 시나리오 블록이 가로챔 (5-12) |
| "OpenClaw에 연결되지 않았습니다" | 릴레이 도달했으나 페어링 문제 (5-14, 패치 후엔 안 나와야 정상) |
| 존댓말 자연어 답변 | 노바 정상 작동 |

### 5-17. 손님 문의 알림은 카카오 앱으로 받는다 (2026-08-21)
블록이 처리하는 말은 릴레이에 오지 않으므로(5-12), 손님이 "상담원 연결"을 요청해도 **우리 시스템은 알 수 없다.** 「상담원 연결」 블록 문구가 "확인 후 답변드리겠습니다"인데 정작 확인할 장치가 없었다.

→ 카카오 공식 앱의 푸시 알림으로 해결했다. 만들 것이 없고 모든 문의를 빠짐없이 받는다.

**앱 이름이 세 가지라 찾기 어렵다.**

| 어디서 | 이름 |
|---|---|
| 옛 이름 | 카카오톡 채널 관리자 |
| 플레이스토어 | 카카오비즈니스 파트너센터 |
| 폰 앱 목록 | **파트너센터** |

→ 폰 `설정 → 애플리케이션` 에서 찾을 때는 **"파트너"** 로 검색할 것. "카카오톡 채널 관리자"나 "카카오 비즈니스"로는 안 나온다.

**켜야 하는 것 두 군데** — 앱 안과 폰 설정, 두 겹이다. 앱에서만 켜면 폰이 막는다.

```
앱 안  : 알림 · 1:1 채팅 · 앱 실행 중 알림 · 고객활동
폰 설정: 알림 허용 · 소리/진동 · 잠금화면 · 알림 팝업
         배터리 → 제한 없음   ← 필수
```

**배터리를 "제한 없음"으로 두지 않으면 알림이 늦거나 아예 오지 않는다.** 안드로이드가 앱을 재우기 때문이다. 공기계 mbot이 3달간 조용히 멈췄던 원인과 같다.

## 6. 발신자에 따른 에이전트 분기

같은 채널에서 **주인은 푸름이, 손님은 노바**가 응대한다. 5-11의 하드코딩 줄을 이렇게 바꿔 두었다.

```js
// dist/src/adapters/gateway.js — buildMessageContext()
const __ownerUserId = process.env.OPENCLAW_TALKCHANNEL_OWNER_USER_ID || '';
const __agentId = (__ownerUserId && normalized.userId === __ownerUserId) ? 'main' : 'nova';
const sessionKey = `agent:${__agentId}:kakao-talkchannel:dm:${normalized.userId}`;
```

주인 식별자는 코드가 아니라 `~/.openclaw/.env`에 둔다.

```
OPENCLAW_TALKCHANNEL_OWNER_USER_ID=MDP4xD-HhFfe
```

이 값은 릴레이 DB에서 확인할 수 있다.

```sql
SELECT normalized_message->>'userId', normalized_message->>'text'
FROM inbound_messages ORDER BY created_at DESC LIMIT 5;
```

동작 확인: 루카가 물으면 푸름이("집사야~"), 다른 사람이 물으면 노바(존댓말). 손님 쪽은 다른 카카오 계정으로 채널에 말을 걸어야 검증된다.

## 7. 노바의 성격

`~\.openclaw\workspace\nova\SOUL.md`에 정의. 요지:

- 존댓말. 상대는 손님(사장님)이다.
- 3~5줄로 짧게. 카톡 화면은 좁다.
- 기술 용어를 쓰지 않는다.
- **마크다운 기호를 쓰지 않는다** — 카톡에서 `**`가 그대로 보인다.
- 모르는 것을 지어내지 않고, 돈이 걸린 약속을 하지 않는다. 그럴 땐 상담원 연결로 넘긴다.
- 근거는 랜딩페이지 FAQ(비용·기간·기존 도구 연동·유지보수).

## 8. 검증 상태

| 구간 | 상태 |
|---|---|
| 루카 → 푸름이 | ✅ 확인 (김치찌개 응답) |
| 루카 → 노바 | ✅ 확인 (분기 넣기 전, 존댓말 응답) |
| 손님 → 시나리오 블록 | ✅ 확인 (지인 3명, 고정 문구 정상) |
| 손님 → 릴레이 → 오픈클로 | ✅ 확인 (가상 손님, `Received message` 로그) |
| 손님 → **최종 답장 배달** | ✅ **확인 (2026-08-21 21:09)** |

**전 구간 검증 완료.** 실제 손님(채널을 갓 추가한 지인)이 "테니스라켓 비싼거 얼마해"를 보냈고, 대기 메시지에 이어 노바가 존댓말로 답했다. 페어링을 한 번도 하지 않은 신규 손님이 자동 연결(5-14)되어 상담까지 이어진 것이 실전에서 확인됐다.

```
21:09:09  수신 delivered  (손님 YTt4Tq81y26V)
21:09:22  발신 sent       ← 13초
```

응답 형태도 설계(7절)대로였다. 존댓말, 3문단, 마크다운 기호 없음, "사장님" 호칭 유지.
